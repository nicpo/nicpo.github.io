# TLDR
{: .no_toc}

- Deterministic grader and an LLM judge can both accept an agent output while missing a flaw that appears under a valid change in conditions.
- I took SQL queries generated by the agent and tested them against valid changes to the database.
- One query both passed the deterministic grader and received a `CORRECT` judge verdict, yet a valid database change exposed a wrong result.
- The learning is to inspect some cases where graders agree. Ask critically what each check actually observed and what legitimate case could make an accepted output fail.

# The setup

My project uses a text-to-SQL agent and a small database about tribute in the Roman Empire. A user asks a question in ordinary language; the agent writes and runs SQL, then explains the result. The eval set has approved reference queries, often called *gold SQL*.

Two checks matter here:

- **Execution accuracy (EX)** runs the agent’s SQL and the gold SQL on the database and compares their results.
- **The false-positive LLM judge** reviews an EX pass. Its job is to spot SQL that got matching results for the wrong reason.

In an [earlier post](https://nicpo.github.io/2026/07/20/ex-vs-llm-judge), I looked at cases where EX and the judge disagreed. This time I looked at *agreement*. The agent ran on the original database, EX passed, and the judge said `CORRECT`. But the agent's SQL was wrong: when the database was slightly changed (while still keeping the schema valid), the query returned a wrong result.


# What the original data didn't show

The accepted query summarized tribute across records for each province. The important difference is this part of the `SELECT`:

```sql
-- Gold: add the shortfalls that are known for individual records
SUM(amount_owed - amount_collected)

-- Agent: subtract two independently calculated totals
SUM(amount_owed) - SUM(amount_collected)
```

With complete records, those expressions agree. That was true of the original data in the database. EX compared the resulting rows, found a match, and passed the query.

But SQL does not treat an unknown value as zero. If either amount in a record is `NULL`, that record’s `amount_owed - amount_collected` is unknown. `SUM` leaves that unknown shortfall out.

Suppose a ledger for the province of Lusitania contains these entries:

| record | amount_owed | amount_collected | known_shortfall |
| --- | ---: | ---: | ---: |
| A | 500 | 450 | 50 |
| B | unknown | 20 | unknown |

The two expressions calculate different things:

- **Gold: 50.** Record A has a known shortfall of `500 - 450 = 50`. Record B’s shortfall is `NULL - 20 = NULL`, which `SUM` skips. The sum of known shortfalls is therefore 50.
- **Agent: 30.** `SUM(amount_owed)` is 500 because it skips B’s unknown owed amount. `SUM(amount_collected)` is `450 + 20 = 470`. `500 - 470 = 30`.

Before calling this mismatch a bug, I needed to check the domain rule and the approved query. Otherwise, a contrived or invalid row could make a sound query look wrong.

# How I found this case

I ran the real agent on 61 questions from the eval set against the original database and saved the SQL it produced. All 61 runs produced SQL without an agent error. Of those queries, 22 passed EX.

I then tested those 22 saved queries against 16 independent, small changes to copies of the original database. The changes were meant to exercise permitted states that the original data might not contain (e.g. a nullable field that contained no `NULL` records)

That gave me 22 × 16 = **352** query-and-database comparisons. Eight comparisons produced a different result from the corresponding gold query. They involved four distinct agent queries. I reviewed those four against the task wording, the data change, and the gold SQL before treating their mismatches as meaningful.

Finally, I sent those four candidates through the existing LLM judge, using the original question, schema, gold SQL, and agent SQL. The judge was not shown the changed rows or the counterexamples. It called three queries `FALSE_POSITIVE` (so they wouldn't pass the eval). It called the query discussed here `CORRECT` - meaning both EX and the judge ok'd it.

# Why did the judge accept it?

The judge’s reasoning treated the two aggregate expressions as equivalent in regular cases. In ordinary, complete rows, they are. The missing case was a valid record with a partially unknown amount.

The judge was asked to look past a matching result and consider whether the SQL logic could fail on plausible data. It had the question, schema, and both queries, but no example of the partial record. Its verdict hinged on 1) an assumption of no `NULL`s in the data, and 2) knowledge that the two `SUM`s behave differently.

The reason why the judge accepted this query can be found in its reasoning, saved in the traces. It wrote:
> `SUM(tr.amount_owed) - SUM(tr.amount_collected)` is logically equivalent to summing the shortfall across rows in ordinary cases.

It appears to have taken an algebraic shortcut: subtracting the totals looked like another way to sum the shortfalls. That works for complete records. The judge did not follow the arithmetic through a valid record where only one amount was known.

# So, should you do anything when graders agree?

I want deterministic checks: EX is cheap, reproducible, and catches plenty of errors. I also want a judge where the task requires interpretation.

The change is in what I do with their *agreement*. A double agreement is evidence about the case they assessed, with the conditions they could observe. It is a useful result, but it has a scope.

For important tasks, I’d put some eval QA effort into apparently settled cases, not only the disagreements:

1. **Write down what each pass proves.** Did a test compare outputs on one fixture? Did a judge inspect the task and artifact, or did it see the environment and outcome too? What assumptions were left implicit?
2. **Challenge a sample of passes.** Keep the agent’s output fixed when checking the *graders*, then ask what permitted change in inputs or environment would make that output fail the user’s goal. For a coding agent, that might be an untested input; for a browser agent, a valid change in page state. Rerunning the agent under those conditions is a separate test of whether the *agent* adapts.
3. **Review before adding a failure.** A counterexample is only persuasive if the changed condition is valid and the task’s expected behavior is clear. Check the reference answer and domain rule, then turn confirmed cases into regression coverage or a sharper grading criterion.

This is not a call to exhaustively search every possible world. It is a way to ask a question of high-confidence results: **what legitimate case would make this accepted output wrong?**

In this run, a real agent query passed EX on the original database and received one accepting verdict from the production SQL judge. A valid database change, with the query held fixed, showed that its logic was wrong.

The lesson I’m taking to other evals is to inspect some double passes for assumptions both checks may have left untouched.

Agreement is valuable. Understanding its limits makes it more useful.
