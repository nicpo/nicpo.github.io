# TLDR
{: .no_toc}

- I tried Jev as an LLM judge. It returns a typed choice and probabilities instead of generated text.
- Compared with GPT-6.1 Sol, judge, Jev was more than 20x faster and about 60x cheaper, but agreed with my labels less often: 89.3% versus 94.9%.
- Most of Jev's errors were false positives: wrong SQL that it let pass.
- Splitting one big decision into narrower questions, as TypeSafe recommends, did not make Jev more accurate.
- Used as a first pass, with low-confidence cases sent on to Sol, it matched Sol's accuracy at about 60% of the cost and latency.

Experiment code: [exp_04_jev_judge](https://github.com/nicpo/ai-agent-evals/tree/main/experiments/exp_04_jev_judge)

# Why try a different judge

My agent answers questions about a small Roman Empire database by writing SQL. I first check execution accuracy (EX): does the agent's query return the same result as the gold query? An LLM judge then reads the SQL to catch cases that EX cannot settle, such as a query that returns the right rows for the wrong reason or a valid alternative that EX rejects.

That LLM judge is expensive. In the [cost post]({% post_url 2026-09-17-costs %}), the judge (GPT-6.1 Sol) cost $1.83 for 535 verdicts, compared with $6.43 to run the agent. Most of the bill came from output tokens: the judge wrote out its reasoning for every case.

The reasoning this judge writes is useful, as it often points to the exact bug. But the scores ultimately depend on a much smaller output: the verdict (`ACCEPTABLE`, `FALSE_POSITIVE` etc.). Given the question, schema, gold SQL and agent SQL, the judge chooses one of a few labels. That makes the task look like classification. I wanted to know whether a model that returns only a label could make the same decisions, and if I'd lose anything along with the explanation.

# What Jev is

Jev is a model from TypeSafe, which calls it a ["System One Model"](https://typesafe.ai/blog/introducing-system-one-models-and-jev): structured state in, typed probabilistic decisions out. Rather than writing a conventional prompt, you send two objects ([API docs](https://api.typesafe.ai/docs)):

- `state` contains the evidence to judge. Here, that meant the question, schema, gold SQL, agent SQL and, when EX failed, both result sets.
- `questions` defines the decision as a type. I used one `choice` with options A, B and C, each described by a written criterion.

Jev returns the chosen option, a probability for each option, and a confidence score:

```json
{"choice": "A", "confidence": 0.91, "probabilities": {"A": 0.94, "B": 0.05, "C": 0.01}}
```

My code maps A, B, and C to `CORRECT`, `INCORRECT`, and `CANNOT_DETERMINE`. Using neutral option names keeps the label names from swaying the choice. Jev received the same evidence as the GPT judges, so the comparison focuses on how the models use it.

TypeSafe recommends splitting a decision into several narrow questions, such as whether the join and filter are each right. My main experiment kept it to one question so Jev could take GPT's place in the existing pipeline. A later section tests the split version.

# Setup

I started with the 549 agent attempts from the [repeatability post]({% post_url 2026-08-28-repeatability %}): 61 questions x 3 agent versions x 3 runs. 14 of them hit the tool-call limit and produced no SQL, so they count as failures without a judge. The other 535 often produced identical SQL for the same question, across runs and sometimes across versions. There's no point judging the same SQL twice, so I grouped those attempts into 196 unique cases. A verdict then applies to every attempt in its group, which is how the judge scores feed back into the per-version results below. I labeled each case myself without seeing any judge's verdict.

Jev (`jev-1.13.0`) judged every case three times, and I took the majority verdict. Sol judged every attempt once, so for a case covering several attempts I took its majority verdict. Both judges used the same evidence. Sol used the same rubric prompt as earlier posts.

# Jev alone

The speed and cost advantage was substantial:

| | GPT-6.1 Sol | Jev |
| --- | ---: | ---: |
| Median latency | 4.5 s | 0.2 s |
| p95 latency | 10.4 s | 0.3 s |
| Cost per 1,000 verdicts | $3.72 | $0.06 |

(Jev's output tokens are free as of Sep 2026, so this is its full cost.)

Accuracy tells a different story. Jev agreed with my labels on 89.3% of cases, compared with 94.9% for Sol. On the 23 cases where the judges disagreed with each other, my label sided with Sol 17 times. More consequential than the overall gap was the direction of the errors:

- **Sol:** 6 false accepts, 4 false rejects
- **Jev:** 17 false accepts, 4 false rejects

In this harness, the judge is the last check before a verdict feeds the score. A false reject sends a query back for review; a false accept can make a wrong result look correct. Jev made almost three times as many false accepts as Sol, so its lower cost comes with a particular risk for a correctness check.

Jev also behaved differently in two ways that an accuracy figure does not capture. It never chose `CANNOT_DETERMINE`, even though that option was available. And it offered no explanation. Sol's reasoning often identifies the bug, for example that a filter drops records with no recorded reason. With a Jev verdict, I have to inspect the SQL myself to understand what happened.

# Can splitting the decision help?

I also tried the approach TypeSafe recommends. I turned the four evaluation dimensions in my GPT rubric (for example, "does the agent SQL apply every condition in the question and no extra ones?") into yes/no questions for Jev, and froze them before running. Jev answers each question independently, so it can't see the other answers. I tried two ways to get a verdict from them:

1. A second call that passes the four answers back as extra evidence for the original question ("two-call"), and
2. A rule in code that accepts a query only if every narrow question passes ("assembled"), using either the lowest probability or the product of all four.

Each variant ran three times per case, with majority votes.

| Judge | Accuracy | False accepts | False rejects | $ per 1,000 | Mean latency |
| --- | ---: | ---: | ---: | ---: | ---: |
| GPT-6.1 Sol | 94.9% | 6 | 4 | $3.72 | 5.9 s |
| Jev, one question | 89.3% | 17 | 4 | $0.06 | 0.2 s |
| Jev, two-call | 88.8% | 9 | 13 | $0.13 | 0.4 s |
| Jev, assembled (lowest probability) | 39.8% | 11 | 107 | $0.06 | 0.2 s |
| Jev, assembled (product) | 31.6% | 0 | 134 | $0.06 | 0.2 s |

Neither approach improved accuracy. The two-call version swapped false accepts for false rejects: 9 instead of 17, but 13 instead of 4. The assembled rules rejected almost everything. One of my narrow questions, about whether differences in output columns were acceptable, got a low "yes" probability on almost all of the queries I had labeled correct, and a single low answer sinks the whole verdict. Looking at the narrow answers afterwards, two questions did separate correct from incorrect queries well: whether the agent returned the same entities, and whether it honored every qualifier in the question. But that's after the fact, on the same 196 cases, so it's a hint for a follow-up experiment rather than a result.

# Jev first, Sol for low-confidence results

Jev's confidence score offers another way to use it. Instead of accepting every verdict, you can keep the high-confidence ones and send the rest to a reasoning model like Sol or Claude. I simulated that cascade from the completed runs: cases below a chosen threshold take Sol's verdict, and the latency estimate assumes the calls run sequentially.

| Setup | Accuracy | False accepts | False rejects | Sent to Sol | $ per 1,000 | Mean latency |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Sol only | 94.9% | 6 | 4 | 100% | $3.72 | 5.9 s |
| Jev only | 89.3% | 17 | 4 | 0% | $0.06 | 0.2 s |
| Jev + Sol below 0.8 | 94.9% | 7 | 3 | 43% | $1.88 | 3.2 s |
| Jev + Sol below 0.9 | 95.4% | 6 | 3 | 56% | $2.28 | 3.8 s |
| Jev two-call + Sol below 0.8 | 95.4% | 6 | 3 | 46% | $1.94 | 3.4 s |

At a 0.9 threshold, the cascade matched Sol's accuracy while cutting cost by 39% and mean latency by 36%. At 0.8 it cut cost roughly in half, and most cases avoided Sol altogether, so the median case was judged in 0.2 seconds. The two-call version performed about the same as the one-question version in the cascade, so the extra call isn't worth it.

The cascade did not improve on Sol's verdicts in any way that matters. Jev made two mistakes above the 0.9 threshold, and Sol got those cases wrong too. Also, I chose these thresholds after looking at the results. In a deployed system, you want to choose a threshold on one labeled sample and evaluate it on another.

The savings are also smaller than they would have been against GPT-5.4. Sol costs roughly a third as much per verdict, so a cheap first pass has less to save.

## Examples of caught and missed errors

Here are fictional versions of real cases. (The actual eval questions stay private so models cannot learn them.)

**1. Error caught.** The question asks, "How many desertions were recorded for each reason, and how many soldiers were lost in total?" The agent adds a filter that nobody requested:

```sql
SELECT desertion_reason, COUNT(*), SUM(soldiers_lost)
FROM desertions
WHERE desertion_reason IS NOT NULL   -- added "to be safe"
GROUP BY desertion_reason
```

No desertion in the current data lacks a reason, so EX passes. Sol rejects the query because a future desertion with no recorded reason would be dropped. Jev accepts it with 0.50 confidence. Because that is below the threshold, the case goes to Sol and the cascade catches the error.

**2. Error missed.** Another question asks which legions saw their grain deficit grow in their latest campaign season compared with the season before. The gold SQL totals each legion's deficit by season. The agent ranks individual deliveries instead, so its "latest" and "season before" can be two deliveries from the same season. EX fails. Jev nevertheless calls the query acceptable with 0.95 confidence, keeping it from reaching Sol, and Sol accepts it as well.

Together, these cases show what confidence routing can and cannot do. It catches a low-confidence false accept, but a confident mistake still passes through, and the fallback judge may share that mistake.

# The judge changes the agent's score

Every verdict contributes to an agent score, so the choice of judge can change the apparent result of an experiment. Here is each agent version's score under different graders:

| Graded by | v1 | v2 | v3 |
| --- | ---: | ---: | ---: |
| My labels | 76.0% | 73.2% | 78.7% |
| GPT-6.1 Sol | 78.1% | 74.9% | 78.1% |
| Jev, one question | 78.7% | 84.7% | 83.1% |
| Jev, two-call | 71.0% | 76.5% | 75.4% |

Jev, one question, scores v2 11.5 points above my labels. Its false accepts have become a much more flattering headline number. The two-call version errs the other way, scoring every version lower than my labels do, because of its extra false rejects. Sol stays within about 2 points of my labels on each version and gets v2 lowest, as I do, but it ties v1 with v3 where I put v3 ahead. The versions are only a few points apart, and the [repeatability post]({% post_url 2026-08-28-repeatability %}) showed that differences of this size are within the noise.

*Scores differ from the repeatability post because I've since corrected two gold queries, and each unique case gets one verdict here.*

# Takeaways

- **Validate a new judge against human labels.** Agreement with the old judge shows how often they match, not which one is right.
- **Check the direction of its errors.** For a correctness check, 90% accuracy with mostly false accepts carries a different risk from 90% with mostly false rejects.
- **Measure the decision the judge feeds.** A dozen extra false accepts turned into an 11.5-point boost for one agent version.
- **Use confidence to decide when to escalate.** Sending uncertain cases from a cheap judge to a more capable one matched Sol's accuracy at about 60% of the cost and latency, though it could not catch errors shared by both judges.
- **Re-check your baseline.** A newer judge cut the cost of the expensive option by about two thirds, which shrank the savings from the cheap one. The cheap-judge case depends on what the alternative costs today.
- **Typed output solves the format problem, not the judgment problem.** Jev never returned a malformed answer, yet it was wrong on about one case in ten. Asking narrower questions didn't fix that, at least in my first attempt.

The same questions arise beyond SQL. A small classifier could grade support-bot replies, or a cheap model could screen code changes before review. In either setting, the useful questions are which errors the judge makes, how those errors affect the decision you care about, and whether its confidence helps identify cases worth escalating.

The cascade itself is not new. [FrugalGPT](https://arxiv.org/abs/2305.05176) (Chen, Zaharia and Zou, 2023) sends queries to cheap LLMs first and escalates when an answer looks unreliable. [Trust or Escalate](https://arxiv.org/abs/2407.18370) (Jung, Brahman and Choi, 2025) applies the idea to LLM judges and calibrates thresholds on a small human-labeled set so the cascade agrees with humans at a guaranteed rate.
