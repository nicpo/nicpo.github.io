# TLDR
{: .no_toc}

- Putting the database schema in my text-to-SQL agent's prompt halved its LLM calls
- In 549 repeated attempts across three agent versions, LLM calls fell 49% and output tokens 27%, but input tokens fell only 5% and the dollar cost 11%
- The reason: every remaining call carried the full schema plus the whole conversation so far
- Nearly all of the saving came from attempts where the old agent kept calling tools until it hit its limit and failed, not from making ordinary answers cheaper
- Grading the attempts with an LLM judge cost almost as much as running the agent

Experiment code: [exp_03_repeatability_costs](https://github.com/nicpo/ai-agent-evals/tree/main/experiments/exp_03_repeatability_costs)

# Half the calls, 11% off the cost

My text-to-SQL agent answers questions about a small database of the Roman Empire: provinces, officials, decrees and tribute records. In the <a href="{% post_url 2026-08-28-repeatability %}">companion post</a> I ran three versions of it on 61 questions, three times each, and looked at accuracy. This post looks at cost. Two versions matter here:

- **v1** gets no description of the database, not even the table names. It has two tools: `get_sample_rows(table)`, which returns three rows from a named table, and `run_query(sql)`, which runs a read-only query. It has to find the tables and columns through these tools before it can write the query that answers the question.
- **v3** has the full schema (tables, columns and their descriptions) in its system prompt, so it can often write the answering query on its first call.

v3 made far fewer calls:

| Per attempt | v1 | v3 | Change |
| --- | ---: | ---: | ---: |
| LLM calls | 4.9 | 2.5 | -49% |
| Tool calls | 5.1 | 1.7 | -66% |
| Output tokens | 656 | 479 | -27% |
| Input tokens | 8,676 | 8,265 | -5% |
| Cost per 1,000 attempts | $11.96 | $10.66 | -11% |

Half the calls, but only 11% off the bill. And *that 11% might be noise*: the 95% interval runs from a $3.04 saving to a $0.53 increase per 1,000 attempts. (Intervals resample the 61 questions, keeping each question's runs together. Costs are agent inference at list prices for Claude Haiku 4.5: $1 per million input tokens, $5 per million output. Database queries cost nothing extra.)

# Every LLM call resends the conversation

The gap comes from how an agent loop is billed. In this harness, each LLM call sends the whole conversation so far: the system prompt, the question, and every earlier tool call and result.

```text
input tokens billed = sum over all calls of (everything sent in that call)
```

So the total depends on two things: how many calls there are, and how large each one is. A few large calls can cost as much as many small ones:

- **v1's calls start small.** Its first call averages about 1,030 input tokens. Sample rows are short, so each later call grows by only a few hundred tokens. But it makes almost 5 calls.
- **v3's calls start large.** The schema raises its first call to about 2,760 tokens, and the schema is sent again on every later call. It makes 2.5 calls.
- **Per call, v3 sends almost twice as much:** about 3,330 input tokens against 1,770 (total input divided by total calls).

Half the calls times twice the tokens per call: input barely moved. Here you can see two real attempts, each representative of its version's typical call count (5 for v1, 2 for v3) and near-median token usage among attempts of that length. v3's system prompt embeds the full schema up front, which is a fixed, larger cost paid once per call. v1 discovers it turn by turn through tool calls, resending an ever-growing conversation instead.

Output tokens are what the model writes: reasoning, tool requests and the final answer. Fewer calls meant 27% less output, and that interval excludes zero.

# From tokens to dollars

Output tokens cost five times as much as input tokens, so you might expect the 27% output cut to affect the cost a lot. As it happened, it didn't, because output is the smaller part of the bill:

| Per 1,000 attempts | v1 | v3 | v3 minus v1 (95% interval) |
| --- | ---: | ---: | ---: |
| Input | $8.68 | $8.27 | -$0.41 (-$1.80 to +$1.01) |
| Output | $3.28 | $2.39 | -$0.89 (-$1.27 to -$0.43) |
| **Total** | **$11.96** | **$10.66** | **-$1.30 (-$3.04 to +$0.53)** |

Input was 73-78% of the bill. The output saving is real, but it applies to the remaining 22-27%.

Two more comparisons:

- **Against v2**, which fetched the schema with a tool call, v3 was cheaper by 5.2%, and that interval excluded zero. v2 received the schema as a tool result, so it cost an extra LLM call to fetch and was then resent with every later call.
- **Per success**, v3 looks better, because it was also more accurate: $16.80 vs $13.70 per 1,000 successful attempts, down 18% (interval: -38% to +7%). This is [cost-of-pass](https://arxiv.org/abs/2504.13359) (Erol et al., 2025): cost per attempt divided by the chance of success. It's a real production cost only if something can detect a wrong answer and retry. Without a validator, you pay for the wrong answers and never learn which ones they were.

# The saving came from failed v1 attempts

So where did the saving come from? I paired every v1 attempt with v3's attempt on the same question and run, then sorted the pairs by which version got it right:

| Pair outcome | Pairs | Mean v3 minus v1 tokens | Total |
| --- | ---: | ---: | ---: |
| Both right | 106 | +515 | +54.6k |
| Both wrong | 17 | -485 | -8.3k |
| Only v1 right | 24 | +267 | +6.4k |
| Only v3 right | 36 | -4,456 | -160.4k |
| **All pairs** | **183** | **-588** | **-107.6k** |

When both versions got it right, v3 used *more* tokens. The entire net saving, and more, came from the 36 pairs where v1 failed and v3 succeeded. In dollars, those 36 pairs account for 86% of the net saving.

<img src="/assets/2026-09-17-costs/v3-v1-diff-sources-waterfall.png" alt="Where the v3-v1 total-token difference comes from" style="max-width: 800px; width: 100%; height: auto;">

What did an expensive v1 failure look like? Here's a hypothetical example (I didn't publish the real eval questions). Take the question "Which governor oversaw the largest tribute shortfall in 50 AD?".

* v1 fetches sample rows from `provinces`, then `officials`, then `tribute_records`
* It writes a query that joins on a column that doesn't exist and gets an error
* It fetches sample rows again to check the column names, rewrites the join, gets an empty result, and tries another filter on the year

Each of those steps is another LLM call, and each call re-sends everything before it. After 12 tool calls the harness stops the attempt.

That happened in 14 of v1's 183 attempts. They averaged about 19,000 tokens, more than twice a normal v1 attempt, and made up 15% of v1's spend. v3 never hit the limit. Those 14 pairs alone account for about three-quarters of the net token saving.

Difficulty shows the same pattern. v3 was cheaper on medium and hard questions, where v1 made the most tool calls, and more expensive on easy and extra-hard ones.


# Grading cost almost as much as the agent

Every completed attempt also went to an LLM judge (GPT-5.4, $2.50 per million input tokens and $15 per million output). The agent cost **$6.43** for 549 attempts. The judge cost **$5.50** for 535 verdicts.

The judge's bill has the opposite shape to the agent's. About 75% of it is output, because the judge writes out its reasoning for every verdict. And three repeats triple both bills.

One cheap fix: cache verdicts for identical SQL. As we have <a href="{% post_url 2026-08-28-repeatability %}">seen earlier</a>, that also stops the judge from grading the same query two different ways.

# Takeaways

- **"Cost" is several numbers.** Calls, input tokens, output tokens, dollars and cost per success described one change as -49%, -5%, -27%, -11% and -18%. Report them separately.
- **Weigh tokens by price and by where they come from.** In an agent loop where the conversation is resent on every call, input tends to dominate the bill. A big output cut can barely change the total.
- **Upfront context trades a variable cost for a fixed one.** The schema in the prompt costs the same on every call. It pays off when it replaces many exploratory tool calls, and it's pure overhead when the agent would have needed only one or two.
- **Look at the failures, not just the mean.** The saving came from attempts where the old agent kept exploring until it hit the tool-call limit.
- **Keep the eval's bill separate from the agent's.** Judge cost grows with every rerun.

There are broader lessons than SQL here. A coding agent can get a compact API spec upfront or search the repository call by call. A support agent can carry the whole policy manual in its prompt or look up one section at a time. Anthropic's piece on [context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) frames this as upfront loading vs. just-in-time retrieval. Counting calls won't settle which is cheaper. Measure tokens per call, the price of each token type and the failures you avoid.

One design I didn't test: prompt caching could make a large fixed preamble much cheaper. It doesn't apply here, because v3's prompt (about 2,760 tokens) is below Haiku 4.5's [4,096-token caching minimum](https://platform.claude.com/docs/en/build-with-claude/prompt-caching). A bigger schema would cross it, but that's a different exercise.
